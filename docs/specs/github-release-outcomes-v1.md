# Governed GitHub release outcomes v1

Status: implemented release infrastructure; not yet exercised against the production repository. This is a dedicated four-operation release saga, not a general GitHub issue, pull-request, ref, or workflow runner.

## Opaque request surface

The aliases are exactly `github_release_candidate_publish_v1`, `github_release_pr_ensure_v1`, `github_release_pr_merge_v1`, and `github_release_tag_create_v1`. Their authority request retains the closed `jobRef`, `requestId`, `sourceRefs`, and `choices` surface. `choices` is exactly `{}`. Resolvers accept only an opaque authorization reference and project only a host authorization handle. Repository, refs, package/version, metadata, limits, allocation identities, credentials, and bytes cannot enter through choices.

Each alias has a distinct definition digest, resolver identity, endpoint, and signed effect. The ordinary MCP invocation is compiled into one of those four endpoints; a host-owned composite adapter preserves the fallback adapter's `prepare`/dispatch/reconcile behavior for ordinary endpoints and replaces only a reviewed release prepared-send callback with the dedicated saga. Release endpoints fail closed when that runner is absent and never fall through to generic HTTPS. The existing dispatch coordinator therefore durably consumes the allocation and commits send-started before the saga can call a provider; a consume or commit failure cannot enter runner recovery. The release publication wrapper alone holds a private confirmation capability and confirms the coordinator's returned receipt reference and evidence digest only after publication succeeds. Direct runner calls, recovery, lookalike objects, and concurrent requests cannot mint that confirmation. A later stage requires it for its predecessor, so provider evidence alone cannot bridge a crash before receipt persistence. Before provider dispatch the runner requires a runtime-verified authorization brand and the authenticated execution context's exact signed allocation ID, allocation digest, effect, and `maxEffects: 1`. Raw objects and stale authorization refuse before GitHub or npm calls.

## Signed operation plan

`ReleaseOperationPlanV1` is a closed `release-authorization` artifact linked by `ReleaseAuthorizationBundleV1.operationPlanDigest`. It binds repository/base/refs/tag/package/version; the base commit and its exact read-back base-tree SHA; every path, Git mode, SHA-256 content digest, expected Git blob/tree/candidate-commit SHA; fixed author, committer, messages, and timestamps; exact draft PR and squash metadata; exact required checks and path-addressed workflow byte digests; and npm's required pre-publication absence. `createTree` receives the signed base-tree SHA, never the base commit SHA. A squash commit SHA cannot truthfully be known before GitHub creates it. The merge transition instead closes the returned SHA against exact PR, `main`, commit, and tree readback, records it in signed merge evidence, and the tag transition accepts a target only from that verified predecessor.

`candidateTreeDigest` is exactly the authority digest of `{ v: "reelier.release-candidate-tree/v1", files }`, where `files` is the complete ordered list of `{ blobSha, contentDigest, mode, path }`. It is not the Git tree SHA. `expectedTreeSha` separately fixes the Git object. Actual bytes come only from the authenticated opaque source and must reproduce both the SHA-256 digest and Git blob SHA.

## Durable transitions and recovery

Every request has a signed append-only journal. Events use exclusive creation, fsync, an authority-journal signature, monotonic sequence, prior hash, fixed semantic digest, and atomic head. A pending head distinguishes a crash between event and head publication from an inconsistent local head. Gaps, forks, tampering, retained-head tail truncation, or semantic request-ID reuse refuse. Authorization and per-request critical sections use monotonically allocated persistent owner tickets. Released and dead lower tickets are ignored; no contender ever deletes or renames another owner's claim, which removes the check/unlink stealing race. A briefly partial ticket blocks entry and then becomes safely recoverable if its creator crashed. A signed one-effect allocation cannot be replayed under another request ID. This local journal does not claim resistance to an administrator deleting and rolling back every journal file and head together; externally rooted completeness remains unchecked.

Content-addressed blob/tree/commit calls may repeat after a crash because their expected IDs are signed. Branch, PR, merge, and tag intents persist before the potentially ambiguous write. A prior branch/PR intent with no authoritative match remains pending. Merge and tag are never resent after intent: recovery performs authoritative PR/main/commit or tag-ref readback only.

Candidate publication validates the complete authenticated file set before its first write, reads base commit→tree, checks base and destination-ref conflicts, creates content-addressed objects from that base tree and a non-force branch, then reads back ref, parent, and tree. PR ensure prechecks base, candidate ref, and duplicate exact head/base matches, creates or reconciles exactly one draft with exact metadata and head, then explicitly journals, performs, and reads back that exact PR's ready-for-review transition. Merge refuses a draft and requires unchanged base, exact head, exact successful checks and authorized CI workflow digest, already-verified signed full-test/coverage/mutation evidence, squash metadata, and PR/main/commit/tree readback. Tag verifies package metadata, npm absence, the reconciled merge predecessor and exact `main`, and creates one non-force immutable ref. Every consequential write has an intent, fresh base/ref/readback checks, a persisted dispatching boundary, and a second expiry check immediately before dispatch. Expiry after intent is journaled as a refusal. A dispatching write may perform read-only reconciliation afterward, including after expiry, but it may never resend or widen authority.

Provider credentials remain in the injected host provider implementation and never enter the agent request. Provider DTOs, fault DTOs, authorization contexts, arrays, choices, and pack reconciliation are closed inert snapshots; proxies, custom prototypes, accessors, extras, sparse arrays, malformed digests, and unverified statuses refuse without caller execution. Faults distinguish `transport-uncertain` from `definitive-refusal` explicitly; thrown `TypeError` is never treated as transport evidence. An uncertain post-write read remains ambiguous. Exact readback emits authorization-bound signed `ReleaseVerifierEvidenceV1` for `candidate-branch`, `candidate-pull-request`, `merge-exact-sha`, and `tag-immutable-ref`. A provider acknowledgement alone is never evidence. This implementation does not publish npm, MCP Registry, or GHCR artifacts and does not mutate workflows.
