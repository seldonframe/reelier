# Governed GitHub release outcomes v1

Status: implemented release infrastructure; not yet exercised against the production repository. This is a dedicated four-operation release saga, not a general GitHub issue, pull-request, ref, or workflow runner.

## Opaque request surface

The aliases are exactly `github_release_candidate_publish_v1`, `github_release_pr_ensure_v1`, `github_release_pr_merge_v1`, and `github_release_tag_create_v1`. Their authority request retains the closed `jobRef`, `requestId`, `sourceRefs`, and `choices` surface. `choices` is exactly `{}`. Resolvers accept only an opaque authorization reference and project only a host authorization handle. Repository, refs, package/version, metadata, limits, allocation identities, credentials, and bytes cannot enter through choices.

The authenticated HTTP form is `POST /v1/jobs/<percent-encoded-jobRef>/invoke`. The path binds the
opaque `jobRef`; a body may omit it or repeat the exact same value, but a mismatch refuses before
dispatch. The remaining body stays the same closed Outcome request (`requestId`, opaque
`sourceRefs`, and closed `choices`) and cannot supply tenant, requester, parent principal, grant,
allocation, or repository identity. HTTP calls the same `handler.invoke` implementation as the MCP
`reelier_outcome_invoke` tool with the server-authenticated execution context. A missing invoke
handler refuses as unavailable; malformed requests refuse; the raw alias HTTP route remains the
ordinary `handler.outcome` path and therefore cannot bypass signed multi-definition job authority.

Each alias has a distinct definition digest, resolver identity, endpoint, and signed effect. The ordinary authenticated opaque-job invocation is compiled into one of those four endpoints; a host-owned composite adapter preserves the fallback adapter's `prepare`/dispatch/reconcile behavior for ordinary endpoints and replaces only a reviewed release prepared-send callback with the dedicated saga. That adapter/publication composer is package-internal and is absent from the public host barrel. The public `createGitHubReleaseAuthorityRuntime` factory is the supported production composition: it accepts only the exact four-definition configuration and a branded host-owned runner, then exposes the ordinary authenticated opaque-job runtime. The normal CLI host composer carries that explicit runner through unchanged. The profile-governed Cell may inject the same runner for an admitted profile; it does not reinterpret one activated profile as four activations. Release endpoints fail closed when the runner or a durable governed receipt head is absent and never fall through to generic HTTPS. The dispatch coordinator durably consumes the allocation and commits send-started before minting the private prepared-send capability; the public prepared-dispatch and lease factories cannot mint it. Reconciliation likewise consumes a coordinator-minted capability bound to the ledger-reread ambiguous request, allocation, and semantics. Public runner `run`/`recover`, direct adapter dispatch/reconcile, lookalike runners, and an absent runner refuse without provider calls. Receipt confirmation occurs only on a coordinator-minted publication call and only after the returned receipt reference/evidence digest reconcile to the authoritative durable head. A later stage requires that signed confirmation, so provider evidence alone cannot bridge a crash before receipt persistence. Before provider dispatch the runner requires a runtime-verified authorization brand and the authenticated execution context's exact signed allocation ID, allocation digest, effect, and `maxEffects: 1`. Raw objects and stale authorization refuse before GitHub or npm calls.

## Signed operation plan

`ReleaseOperationPlanV1` is a closed `release-authorization` artifact linked by `ReleaseAuthorizationBundleV1.operationPlanDigest`. It binds repository/base/refs/tag/package/version; the base commit and its exact read-back base-tree SHA; every path, Git mode, SHA-256 content digest, expected Git blob/tree/candidate-commit SHA; fixed author, committer, messages, and timestamps; exact draft PR metadata plus `readyForReview: true`; exact squash metadata; exact required checks and path-addressed workflow byte digests; and npm's required pre-publication absence. Draft creation and ready-for-review are two journaled internal subtransitions of the single PR Outcome and its one allocation, never a fifth top-level effect. `createTree` receives the signed base-tree SHA, never the base commit SHA. A squash commit SHA cannot truthfully be known before GitHub creates it. The merge transition instead closes the returned SHA against exact PR, `main`, commit, and tree readback, records it in signed merge evidence, and the tag transition accepts a target only from that verified predecessor.

`candidateTreeDigest` is exactly the authority digest of `{ v: "reelier.release-candidate-tree/v1", files }`, where `files` is the complete ordered list of `{ blobSha, contentDigest, mode, path }`. It is not the Git tree SHA. `expectedTreeSha` separately fixes the Git object. Actual bytes come only from the authenticated opaque source and must reproduce both the SHA-256 digest and Git blob SHA.

## Durable transitions and recovery

Every request has a signed append-only journal. Events use exclusive creation, fsync, an authority-journal signature, monotonic sequence, prior hash, fixed semantic digest, and atomic head. A pending head distinguishes a crash between event and head publication from an inconsistent local head. Gaps, forks, tampering, retained-head tail truncation, or semantic request-ID reuse refuse. Authorization and per-request critical sections use monotonically allocated persistent owner tickets. A creator writes and fsyncs the complete PID/nonce ticket under a private pending name, then atomically hard-links that complete inode into the numbered queue; competing creators cannot overwrite the winning link. A paused creator has not published a ticket and cannot expose partial JSON or block a complete contender. Dead published owners and released lower tickets are skipped. No contender removes or renames another live owner's ticket. A signed one-effect allocation cannot be replayed under another request ID. This local journal does not claim resistance to PID reuse on every host, an administrator deleting the queue, or rollback of every journal file and head together; externally rooted completeness remains unchecked.

The production file publisher persists an immutable reservation root and terminal nodes under an identity-addressed chain. Restart readback derives one authoritative head and refuses forks, unreachable nodes, identity changes, or prior-link conflicts. If a process crashes after that immutable terminal node is committed but before the runner appends `receipt-published`, the restarted publication wrapper adopts only the authoritative acknowledged/reconciled head. It revalidates request ID, effect semantics, authorization digest, alias, exact one-effect allocation, and signed provider evidence, then idempotently appends the missing confirmation. It neither republishes the receipt nor calls the provider. A conflicting confirmation refuses, while an exact repeat converges.

Content-addressed blob/tree/commit calls may repeat after transport uncertainty because their expected IDs are signed. Branch, PR, ready-for-review, merge, and tag intents persist before the potentially ambiguous write. An intent alone never adopts externally created state: an exact branch, PR, ready transition, merge, or tag that appears before the corresponding durable `*-dispatching` event is a conflict. Only a dispatching boundary permits read-only reconciliation of a possibly applied write. Explicit provider refusal is journaled as terminal at every write class and is never converted into ambiguity or resent under the request. Malformed or transport-uncertain write acknowledgement may reconcile only through authoritative readback. Merge and tag are never resent after their dispatching boundary: recovery performs authoritative PR/main/commit or tag-ref readback only.

`reconciliationStatus` describes the four logical Outcomes, not each internal provider call. Confirmed blobs, trees, commits, or a created draft remain partial effects when a later subcall refuses; such an Outcome cannot report `not-applied`. The receipt graph still declares completeness `unchecked`: this records observed governed effects and never claims that every possible provider write passed through Reelier.

Candidate publication validates the complete authenticated file set before its first write, reads base commit→tree, checks base and destination-ref conflicts, creates content-addressed objects from that base tree and a non-force branch, then reads back ref, parent, and tree. PR ensure prechecks base, candidate ref, and duplicate exact head/base matches, creates or reconciles exactly one draft with exact metadata and head, then explicitly journals, performs, and reads back that exact PR's ready-for-review transition. Merge refuses a draft and requires unchanged base, exact head, exact successful checks whose workflow path and digest equal the signed `.github/workflows/ci.yml` commitment, already-verified signed full-test/coverage/mutation evidence, squash metadata, and PR/main/commit/tree readback; the reconciled squash commit parent must equal the authorized base commit. Tag verifies package metadata, npm absence, the reconciled merge predecessor and exact `main`, persists intent, and rechecks package/version and npm absence again immediately before its non-force write. Recovery first reads the exact tag: an already-applied authorized tag reconciles even if its downstream workflow has since published npm, while an absent tag is never resent. Every consequential write has an intent, fresh base/ref/readback checks, a persisted dispatching boundary, and a second expiry check immediately before dispatch. Expiry after intent is journaled as a refusal. A dispatching write may perform read-only reconciliation afterward, including after expiry, but it may never resend or widen authority.

Provider credentials remain in the injected host provider implementation and never enter the agent request. Provider DTOs, fault DTOs, authorization contexts, arrays, choices, and pack reconciliation are closed inert snapshots; proxies, custom prototypes, accessors, extras, sparse arrays, malformed digests, and unverified statuses refuse without caller execution. Faults distinguish `transport-uncertain` from `definitive-refusal` explicitly; thrown `TypeError` is never treated as transport evidence. An uncertain post-write read remains ambiguous. Exact readback emits authorization-bound signed `ReleaseVerifierEvidenceV1` for `candidate-branch`, `candidate-pull-request`, `merge-exact-sha`, and `tag-immutable-ref`. A provider acknowledgement alone is never evidence. This implementation does not publish npm, MCP Registry, or GHCR artifacts and does not mutate workflows.
